# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a Kubescape Headlamp Plugin that integrates Kubernetes security scanning capabilities into the Headlamp dashboard. It provides compliance scanning, vulnerability management, network policy visualization, runtime threat detection, and policy validation through a React/TypeScript frontend with WASM-based policy evaluation.

## Development Commands

### Frontend Development
```bash
npm run start          # Start development server
npm run build          # Build plugin for production
npm run lint           # Run ESLint
npm run lint-fix       # Fix ESLint issues automatically
npm run tsc            # TypeScript compilation check
npm run format         # Format code
npm run test           # Run tests (vitest), once; npm run test:watch keeps running
go -C go test ./...    # Run Go tests of the WASM evaluators
```

The `tsc`, `lint`, `lint-fix`, `format` and `test` scripts run the tools directly with the arguments `headlamp-plugin` uses: on Windows `headlamp-plugin` starts the `.cmd` files of the tools without a shell, which Node refuses since its fix of CVE-2024-27980. CI runs `npx @kinvolk/headlamp-plugin` itself. With `core.autocrlf` the checkout has CRLF line endings, which `prettier --check` reports; `--end-of-line auto` checks the formatting alone.

### WASM and External Dependencies
```bash
make download                              # Download all external dependencies
make build                                 # Build Go code to WASM (requires Go)
make local                                 # Build a copy of the checkout and install it in Headlamp desktop (scripts/install_headlamp_plugin.py --source .; PYTHON=py on Windows)
make wasm-download                         # Copy the WASM execution runtime from the Go toolchain
make kubescape-rego-download               # Download controls, frameworks, and rego rules
make kubescape-cel-admission-library-download # Download CEL admission policy and test files
```

The versions of the Kubescape data (the `cel-admission-library` release and its test resources, the `regolibrary` release) and the test files are pinned in `scripts/data-sources.json`, which the Makefile (with jq) and `scripts/install_headlamp_plugin.py` read and Renovate raises; regolibrary's `v2` release is a rolling one. The installer builds a copy of a checkout (`--source`), so a build does not change it, and puts back what it moved when installing fails.

### End-to-end tests
```bash
npm run e2e:setup   # kind cluster kubescape-e2e, plugin build, Headlamp at http://localhost:4488, waits for the scans
npm run e2e         # Playwright, e2e/tests/*.e2e.ts; report in e2e/playwright-report
bash e2e/build-plugin.sh && bash e2e/headlamp.sh   # after changing src/
```

`npm run e2e:setup` creates the kind cluster `kubescape-e2e` with Kubescape, kube-prometheus-stack and the workloads of `e2e/workloads.yaml` (`setup-kind.sh`), builds the plugin into `e2e/.plugins/headlamp_kubescape` (`install_headlamp_plugin.py --source . --output DIR`, which leaves Headlamp desktop alone), runs Headlamp in server mode in Docker at http://localhost:4488 (`headlamp.sh`, image pinned by digest) and waits for the scans, profiles, alerts and Prometheus totals (`wait-for-scans.sh`, which asks the operator for a configuration scan, as the scheduled one runs daily). First run `npx playwright install chromium`; on a new cluster the scans and alerts take 15–20 minutes. `.github/workflows/e2e.yaml` runs the suite weekly and on demand; Renovate raises the chart versions and the Headlamp image of the setup after two weeks. The e2e test files are `*.e2e.ts`, as `headlamp-plugin test` runs Vitest with Headlamp's config, which collects every `*.spec.ts` and `*.test.ts` of the checkout; `e2e/tsconfig.json` type-checks them (`npx tsc -p e2e`). On Windows `e2e/bash.mjs` finds Git's bash, as `bash` resolves to WSL. The node-agent learns a container for `nodeAgent.config.maxLearningPeriod` (24h by default); `learningPeriod` is only the delay before the first profile is written, so the e2e cluster learns for 3 minutes and the intruder pod alerts some minutes after it starts. Headlamp keeps plugin settings in localStorage `pluginConfigs`, keyed by the package name, and writes them half a second after a change; the e2e tests seed them there. Monaco only draws the lines in view, so e2e tests find text further down with the editor's search (ControlOrMeta+F). The node-agent alerts once per process and domain of a container, and Alertmanager drops an alert an hour after it was sent; `e2e/fresh-alerts.sh`, which `wait-for-scans.sh` and the Playwright global setup run, therefore restarts the intruder when its alerts are gone or about to go and waits about 6 minutes for new ones; a read of Alertmanager that fails is tried again until the timeout, not taken for an answer (`E2E_SKIP_FRESH_ALERTS=1` skips that). The e2e scripts always pass `--context kind-kubescape-e2e`, and `setup-kind.sh` switches back to the previous context after `kind create cluster`.

## Architecture Overview

### Plugin Structure
The plugin integrates with Headlamp through `@kinvolk/headlamp-plugin` framework using:
- **Sidebar registration**: Adds navigation entries for main features
- **Route registration**: Defines URL routes for each feature module
- **Detail view extensions**: Adds security information to existing Kubernetes resource pages
- **Multi-cluster support**: Works with Headlamp's cluster context switching

### Core Feature Modules

#### 0. Overview (`src/overview/`) and setup check (`src/common/SetupCheck.tsx`)
- Landing page of the Kubescape sidebar entry: compliance scores, CVE counts with the top package upgrades, recent runtime alerts and expiring exceptions
- Shares the scan caches of the Compliance and Vulnerabilities pages through `readConfigurationScans` and `readVulnerabilityScans`
- Every feature page starts with a setup check (`kubescapeSetup.ts`) that reports a missing storage API or disabled operator capabilities (read from the `ks-capabilities` ConfigMap) with the Helm command that fixes them
- Scan now / Rescan buttons (`ScanNowButton.tsx`, `operatorCommands.ts`) create an `OperatorCommand` (`kubescape.io/v1alpha1`, command type `OperatorAPI`) in the operator namespace and follow its status
- A vulnerability rescan must be a scope (`wildWlid` of the namespace with `args.labels` of the workload's pods, or `args.fieldSelector` for a bare pod): the operator only works out the containers to scan for a scope, and fails with "failed to get container for image" for a plain `wlid`
- Trends (`Trends.tsx`, `prometheus.ts`) chart the cluster totals of the Kubescape Prometheus exporter (`kubescape_controls_total_cluster_*`, `kubescape_vulnerabilities_total_cluster_*`) with `query_range` through the service proxy to the Prometheus address in the settings. Recharts is provided by Headlamp at runtime. The rows are kept with their cluster, so another cluster does not show the charts of the one chosen before while it is read, and `prometheusAddresses` offers a service only with a server port (9090, or a port named `web`, `http-web` or `http`) or the name or labels of a Prometheus server, which leaves out the services kube-prometheus-stack names after itself for its scrape targets in kube-system. A click on a point of a chart, or Explain the largest change, explains a step (`trendChanges.ts`, `ChangePanel`): the largest change of the chart near the point (`largestChange`, two points either side, as a click seldom hits the point right after a step) is shaded, and a panel compares the totals of each namespace at its two points (`kubescape_vulnerabilities_total_namespace_*`, `kubescape_controls_total_namespace_*`, instant queries `max by (namespace, exported_namespace)`): the workload namespace is in `exported_namespace`, as Prometheus renames the exporter's `namespace` label when it scrapes with the labels of the target, as the ServiceMonitor of the Kubescape chart does (its `namespace` then names the namespace of the exporter), and in `namespace` with honorLabels. It names namespaces that appeared or went, reads the schedule of the daily scan from the operator's CronJob (`kubevuln-scheduler` for CVEs, `kubescape-scheduler` for controls; a plain daily schedule in UTC, `dailyTime`) and says when it last started, and `likelyCause` tells namespaces that appeared or went, most namespaces at once around the daily scan (an update of the vulnerability database) and changes in one or two namespaces apart. The exporter counts the findings of each workload container (one VulnerabilityManifestSummary per workload and container): replicas do not count, and an image counts once for every workload that runs it
- Notifications (`src/common/notifications.ts`, started from `index.tsx`) report critical runtime alerts and exceptions that expire within a week through Headlamp's notification store, every five minutes for all selected clusters: `SelectedClustersTracker`, registered as an app bar action that renders nothing, keeps `useHLSelectedClusters` for the checks, and `clustersInUrl` reads the `/c/a+b` route parameter when it is not mounted (Headlamp's `getClusterGroup` returns only the first cluster). Sent ids are kept in localStorage, because Headlamp marks a notification that is sent again as unseen. A check is not started while one runs, each cluster is checked and sent on its own, so a cluster that does not answer keeps back nothing of the others, and the exceptions are read with `fetchSecurityExceptions` (the allowed namespaces of a restricted user)
- Search (`src/search/`): a button in Headlamp's top bar (`registerAppBarAction`) opens a search of CVEs (by id, a related id such as the CVE of a GHSA, or package), images, workloads (by name or container) and controls. Headlamp's own search has no plugin hook: it finds a fixed list of Kubernetes kinds and the registered pages without parameters, and registering a page per CVE was ruled out (a cluster easily has thousands of different CVEs, which are only in the full reports, hundreds of MB). The first search of a session reads the reports into the cache the Vulnerabilities pages share (`readVulnerabilityScans`); controls are searchable meanwhile. Indexing 8,000 CVEs takes ~30 ms and a search under 20 ms
- Kubescape columns in Headlamp's workload and pod lists (`src/sections/tableColumns.tsx`, `workloadSummaries.ts`, `scannedWorkload.ts`) show critical and high CVEs and failed controls per workload. They are neither sorted nor searched (`sort: false`, a value of `''`): Headlamp's table sorts its rows and takes the values it searches once per change of its data, and the counts of the other namespaces arrive later, so their rows would keep the place of rows without results. Summaries are read per namespace of the rows shown, four namespaces at a time, and kept for five minutes; pods are matched to their workload by the name of their controller (`scannedWorkloadCandidates`): a static pod, which its node owns, is the pod itself, a Job of a CronJob is the CronJob, and the pod itself is the last candidate; the workload page falls back to the first candidate when it cannot read the controller. Where the plugin applies the exceptions itself (riskAcceptance off), the failed controls of the columns and of the workload and namespace page sections (`useFailedControlCounts`, `useNamespaceFailedControls`, the totals of the namespace's workload summaries) leave out the controls that exceptions exclude in every framework (`failedControlCounts`); the exceptions are read once per cluster with the summaries (`readClusterExceptions`, five minutes, 30 s after a failure), and a failure to read them is noted under the counts

#### 1. Compliance (`src/compliance/`)
- Configuration scanning and compliance reporting
- Uses `WorkloadConfigurationScan` and `WorkloadConfigurationScanSummary` CRDs
- Main components: `Compliance.tsx`, `WorkloadScanDetails.tsx`, `ControlResults.tsx`
- A control's fix can be downloaded as YAML or applied after confirmation (`WorkloadScanFixes.tsx`); the update carries the resourceVersion, so a changed resource gives a 409 instead of being overwritten. A resource that changed after the scan gets a warning and no Apply, as the fix paths index what the scan saw (`containers[1]` may be another container now, or one past the end): a WorkloadConfigurationScan carries no resourceVersion or generation of the workload, so the newest time of the resource's managed fields other than subresources (status, scale), or its creation, is compared with the time of the report (`lastChanged`, `scanTime`: the annotation `kubescape.io/report-created-at`, to the nanosecond, else `spec.metadata.report.createdAt`). The resource is read in its own API group and version (the labels `kubescape.io/workload-api-group` and `-api-version`, the `apiGroup` and `apiVersion` of a related object): Headlamp's class of the kind when it is of that group, else the resource discovery names (`resourceLocation`), as kinds of other groups share names (Istio's Gateway and the Gateway API's). A rule path without a value to set (only a `failedPath`, or a `fixPath` whose value the storage left out) changes nothing: it says where the control failed, not what to change, and the fix page lists it as a path to review (`resourcePaths`). The delete and review paths of a rule reach the storage as empty entries, so a `failedPath` alone comes from the rules that only name where they failed, such as the `spec.podSelector` of a network policy that selects no pods. The diff is read-only, and a fix whose value is a placeholder of Kubescape (`YOUR_VALUE`, `REMOVE_GROUP_0`, `<your-tls-definition>`; `isPlaceholder`) can be downloaded but not applied
- Failures to read the security exceptions are shown on every compliance page for the clusters of the page (`ControlExceptionErrors`); `markExceptions` of the workload scan page returns them
- With a framework chosen (not the combined Full Regolibrary view), the header line and the Resources and Namespaces tabs count only the framework's controls (`controlIDs` of `failedControls`, `passedShare`, `countResourceScans`, `getNamespaceResults`, `countFailedScans`, `countExcludedControls`), so counts and tooltips agree. A framework without controls scores 100. The scores shown default to `defaultFrameworkNames` while none are chosen (`activeFrameworkNames`)
- Excluding a control cluster-wide applies the exceptions again. The namespace page reads its cluster with `readConfigurationScans(..., { keepOtherClusters: true })`, so the cache keeps the other selected clusters, and counts its header from the scans of its table rather than the storage summary. A page read for a task the cache dropped is not stored (`isCurrentTask`), and More scans and Reload results only update the page while they are its current read
- The header counts what exceptions exclude as resources and control results (`excludedCountsLine`): `countExcludedControls` counts a control once per resource it is excluded in; the Namespaces tab calls the same count Excluded Control Results. When the fixed YAML of a control equals the resource, as for C-0057, whose rules Kubescape gives no fix path, the fix page says that Kubescape gives no automatic fix instead of showing an empty diff and an Apply that cannot be used

#### 2. Vulnerabilities (`src/vulnerabilities/`)  
- Container image vulnerability scanning
- Uses `VulnerabilityManifest`, `VulnerabilityManifestSummary`, `SBOMSyft` CRDs
- Main components: `Vulnerabilities.tsx`, `CVEResults.tsx`, `ImageDetails.tsx`
- The Upgrades tab (`UpgradeList.tsx`, `upgrades.ts`) ranks package upgrades by the CVEs they fix
- Severity counts link to the findings of that severity with `?severity=`, read with `useURLSearchParam`
- A summary's `vulnerabilitiesRef` can name the workload namespace while the storage keeps all reports in the operator namespace. References are resolved at the referenced namespace first, then by name in the cluster (`findImageScan`) or in the operator namespace, or `kubescape` while that cannot be looked up (`fetchVulnerabilityManifest`, whose fourth item names the reports that could not be read, which the workload page shows as errors)
- Recent kubevuln versions leave `spec.metadata.report.createdAt` of the reports empty; the scan time is the `kubescape.io/timestamp` annotation (Unix seconds) of the summary (`getScanTime`)
- CVEs selected in the CVE list get one cluster-wide exception (`GuidedClusterVulnerabilityExceptionForm` takes `cveIds`), created in each cluster a workload has them in (`clustersWithCves`, `createClusterException`)
- The pages read the summaries of the workloads, then only the reports those refer to (`vulnerabilitiesRef.all` and `.relevant`), each on its own and six at a time (`manifestReader.ts`, `readReferencedManifests` in `Vulnerabilities.tsx`, a task with its own `read` in `query.ts`). The storage reads and decodes the objects of a list one after the other within one request, while it locks per object, so separate requests run in parallel; and a list of all reports also holds those of images that no longer run. References are read once per report name in a cluster (`reportNameKey`): summaries of several namespaces may each name their own namespace for the report of one image, which the storage keeps once in the operator namespace. A report that is not where its reference points is read in the operator namespace, or in `kubescape` while that cannot be looked up; only a report that is in neither namespace of a known operator counts as missing and is not asked for again in the session, while reports that failed, also for an unknown operator, are read again by the next read ("More scans"). The read goes on until no workload of the cluster misses a report, as other reads of the shared cache may add workloads meanwhile; a summary without labels is left out. Workloads are linked to the reports as they arrive (`linkWorkloadScans`, `unreadReferences`)
- Relevance is per CVE and package (`relevance.ts`): the relevant report holds only the packages the workload was seen to use, and a CVE is often in several packages of an image (busybox, busybox-binsh, ssl_client), which Kubescape's relevant counts count apart. The CVE list, which is per CVE, calls a CVE relevant when the report has it in any package
- The page reads the scans again when the selected clusters change, as Headlamp keeps the route mounted from `/c/a` to `/c/a+b`, with a flag per read like the Compliance page. A task that was dropped from the cache (cluster deselected, namespaces changed) keeps the pages it still reads out of it (`isCurrentTask`). `?tab=cves|resources|images|upgrades` opens a tab (`vulnerabilityTabs`); choosing another tab removes it from the address
- A finding may have no CVSS score (`cvss: []`); it counts as 0 (`cvss?.[0]?.metrics?.baseScore ?? 0`)
- The page reads the summaries of all clusters first, then the reports; `readVulnerabilityScans`' `onScans` gets the workloads once the summaries are read and then at most twice a second (`throttle.ts`), so the tabs show while the reports are read, with a `ProgressLine` instead of the spinner. Until its report is read, the Resources tab shows a workload's counts from its summary (`WorkloadScan.summaryCounts`, from `spec.severities`), dimmed and marked `(summary)`; the mark is part of the cell value, so the cell is drawn again when the report brings the same counts
- The reports are kept between sessions (setting `keepVulnerabilityReports`, on unless false) in the plugin's IndexedDB database (`src/common/pluginDatabase.ts`, `kubescape-plugin`; raise its version to add stores in `createStores`). `reportCache.ts` stores the slimmed `ImageScan` keyed by cluster, namespace and name with the report's uid and resourceVersion; a cluster is identified by the uid of its kube-system namespace, or by its name. A read lists the reports' metadata without fullSpec (`listReportVersions`, per allowed namespace plus the operator namespace; the storage returns uid and resourceVersion there and honours `limit`/`continue`), takes the unchanged reports from the store and GETs only the others (`readReports`). Reports unused for 7 days are pruned, at most 5,000 reports and 300,000 findings are kept, and pruning runs at most hourly. Without IndexedDB, or when the metadata cannot be listed, every report is read. Switching the setting off clears the store (`clearReportCache`). Raise `reportFormat` when `toImageScan` keeps other fields
- The Clusters page (`ClusterComparison.tsx`, `imagesAcrossClusters.ts`; sidebar entry under Vulnerabilities, route `/kubescape/vulnerabilities/clusters/compare`, which has four segments so `/kubescape/vulnerabilities/:namespace` does not take it) compares the images of the selected clusters per repository (`imageRepository`: registry/repository without tag or digest, so `nginx` and `docker.io/library/nginx` are one): the versions each cluster runs with their workloads, critical and high CVEs (relevant and all) and fixable CVEs, where the clusters differ, and upgrade candidates. Clusters that run one tag with the same CVEs are one variant, so three clusters on two versions give one difference; two versions within one cluster are not compared. Differences compare the CVE ids of the reports including `ignoredMatches`, as exceptions differ per cluster; the counts are of the open CVEs, as on the image pages. Tags are ordered by `compareTags` (`imagesAcrossClusters.ts`, with `versions.ts`: a date such as `20260805` is a build (`isDate`), not ordered with a version or a release line such as `3`; a leading `v` aside; a release line such as `1.25` is not ordered with `1.25.3`; variants of one version are the same version). Upgrade candidates are per tag (see below), and only to a newer tag; one tag with other reports (a rebuilt image, or a scan with another vulnerability database) is a difference but not a candidate. A selected cluster of which no scans were read is left out instead of counted as missing every image. A workload whose report was not read (missing, failed, or not named by its summary) runs the image its summary names (`kubescape.io/image-tag`, `WorkloadScan.image`), or any image when the summary names none: its cluster is not counted as missing that image, or any image its reports lack (`unknownRepositories`) (`unknownIn`, status `Not in <cluster>'s reports`, counted with Not in every cluster), and a note counts those workloads per cluster and lists them on request (`withoutReports`, `MissingReportsNote`). They are mostly Jobs and CronJobs: the storage removes the report of an image that no pod runs while the summary of the CronJob stays, so between two runs the summary names a report that is gone. With fewer than two clusters selected the page explains how to select several (Home, All Clusters, View Clusters) and reads nothing. It waits for the whole read rather than using `onScans`, as partly read reports would show differences that are not there. The pure module is not named `clusterComparison.ts`, which would differ from `ClusterComparison.tsx` only in case
- Known exploited CVEs and EPSS scores (`exploitData.ts`, `KnownExploited.tsx`): kubevuln's reports have neither, so they are looked up by CVE id (a finding's own id when it is a CVE, else the CVEs of its `relatedVulnerabilities`; `exploitIds`), each behind a setting that is off unless `true` (`knownExploited`, `epss`; `useExploitSettings`), whose text in the settings names the endpoint and what it receives: keep it in step with the lookups. CISA's KEV catalog is downloaded whole once a day from jsDelivr's copy of `cisagov/kev-data` (CISA's own address does not allow other sites) and matched in the browser, so jsDelivr receives nothing about the clusters; a catalog of an earlier day is used when the download fails. EPSS scores come from `api.first.org/data/v1/epss`, which receives the CVE ids the pages show, 80 per request, at most two requests at a time, the lookups of the view that opened last first; switching the setting off revokes the permit of the requests that wait (`changeExploitSetting`, `epssPermit`). Both are kept a day in the `exploitData` store of the plugin's IndexedDB (version 2 added it; the catalog in a compact form, a record per CVE, null when FIRST has no score), and failures an hour in memory. The CVE list, the workload page and the image page show an Exploited chip (date added and ransomware use in its tooltip), an EPSS column (score and percentile), a "Known exploited only" switch and the matching CSV columns; the rows are new objects when the answers arrive (`withExploits`). The Overview counts the known exploited CVEs
- The Clusters page shows its counts as tiles over two tabs, Upgrade candidates and Images (the tab and the filter are kept for the session, `ClusterComparisonTab`, `ClusterComparisonFilter`). A tile of images (`ImageFilter`, `filterRepositories`; the summary counts images, also `newerAddCves`) opens the Images tab with those images, whose Show select offers the same choices, and the Upgrade candidates tile opens that tab. Images are named by their last path segment over the registry and path (`splitRepository`). Two tags are only compared when a cluster runs one of them and not the other (`inOtherClusters`): versions that the same clusters run are no difference between clusters. Upgrades are per tag (`TagVersion`, `RepositoryComparison.tags`, newest first): one tag in several clusters is one version, also when its reports differ in some CVEs (a rebuilt image, or a scan with another vulnerability database), with the CVEs of all its reports (`unionCves`), as listing it once per report made the page hard to read. A tag's `upgrades` are the newer tags, its `others` the tags that cannot be ordered with it (branch builds, a release line such as 18 next to 18.4) and other variants of its version; either needs a cluster that runs one of the two and not the other. An upgrade candidate is a tag with an upgrade that removes CVEs: the newest such tag, the other newer tags as `alternatives`; tags that cannot be ordered are never candidates, as moving production to a branch build or sideways to a release line is no upgrade. The Images tab shows per image a line per tag over all clusters, newest first (`TagLines`): the tag with its clusters under it, its CVEs by severity with its workloads under them, its upstream version and the upgrade to recommend, in columns of a width of their own that fit a table of 1500 pixels (`recommendedUpgrade`, which the candidates and the dialog use too), rather than a column per cluster, which repeated a tag that several clusters run. The Upgrade candidates tab has a row per image (`CandidateRow`, the worst candidate first, which counts how many of all its versions can upgrade, `versionCount`, as the newest versions have no line while the dialog shows them) whose versions that can upgrade are lines of one grid; the column header draws the labels of that grid (`UpgradeHeader`, a `Header` render of the column), and the grid has columns of a width of their own, so the labels and the lines of all images line up. The newest upstream version of each tag (`useUpstreamVersions`, one lookup per tag with `tagLookup`) comes from the lookups of the other image pages (`useImageVersions`), so only while the setting `imageVersions` is on, with its permits and caches; the candidates (under the current version, which saves a column), the lines of the Images tab and the lines of the dialog show it, the rows are new objects when it arrives, and the descriptions name the setting while it is off. The candidates table names where the current version runs: up to three workloads as namespace/name with cluster and container (`candidateWorkloads`; `ClusterVersion.workloadReferences` carries the summary name the vulnerability page of a workload needs), the rest in the dialog. The name of an image, or a click on a row of either table, opens a dialog with the versions of the image as lines of one grid under its labels (`VersionLines`), newest first, like the tabs: per version its clusters (chips that open the report of the tag in that cluster; the chip is inside Headlamp's `Link`, as the link takes no ref), its workloads (five, then all on request), its CVEs and its upstream version, and under it its upgrades (`VersionUpgrades`): the recommended one as Upgrade to, the other newer tags as Also newer, each with what it removes and adds (`DeltaPair`) and its critical and high CVEs unfolding under a CVEs button, as links to their pages unless exceptions hide the CVE in all reports of that version (`CveLinks`), as the page of a CVE lists only workloads whose reports count it, and the other tags folded away under Compare with. A filter of the workloads shows when there are more than eight. Removes and Adds show the CVEs by severity in the boxes of `SeverityCountStack`, each box listing its CVEs. The differences between variants (`VersionDifference`, `describeDifference`) are only in the status, the summary counts and the CSV
- With more than one cluster selected, the Vulnerabilities page links to the comparison of the clusters next to the scans count
- The rows of findings are keyed by `uniqueFindingIds`: a package installed at several paths gives findings with the same CVE, name and version, and rows with the same key stay on the page when a filter removes them. The full reports carry `artifact.id`; the cache does not
- Workloads are named `namespace/name/container`, with the cluster in front when the scans are of several clusters (`workloadLabel`)
- The SBOM page names the distribution with its version (`distroLabel`: `prettyName`, else name and versionID) and downloads the stored Syft JSON document as is, or converted to CycloneDX 1.5 JSON (`sbomExport.ts`)
- Images link to their vulnerability page and to the tag list of their registry (`ImageReference.tsx`, `registry.ts`): Docker Hub, Quay, GitHub, Google, Microsoft and the Amazon ECR public gallery. Other registries, such as registry.k8s.io, have no such page and get no button
- The Images tab and the pages of an image and a workload show the tag, the newest version and the end of life of the release line (`ImageVersion.tsx`, `imageVersionSources.ts`, `versions.ts`). The lookups are split into the cache (`versionCache.ts`), the request queue and its permits (`versionRequests.ts`), endoflife.date (`endOfLife.ts`) and version-checker (`versionChecker.ts`); the views import them from `imageVersionSources.ts`, which tests mock. All three settings are opt-in, off unless they are `true` (`imageVersions`, `endOfLife` under it, and `possiblyPrivateImages`; `useImageVersionSettings`), as they ask services outside the cluster, and the text under each switch names every endpoint and what it receives: keep it in step with the lookups. With `endOfLife` off, `lookupImageVersion` gets `endOfLife: false` and asks endoflife.date nothing, also not for the newest version. The browser may only read services that allow other sites to, and Docker Hub, GHCR, GCR and MCR do not, nor may a plugin run its own script in Headlamp desktop or use its proxy for other hosts than artifacthub.io. So the tags of quay.io images come from Quay's API, those of gcr.io, `*-docker.pkg.dev` and registry.k8s.io (`k8s-artifacts-prod`) images from the API of Google's Artifact Registry, which public repositories answer without a login (`artifactRegistryPackage`; a repository is checked once a day, so a private one costs one request rather than one per image), the tags of Docker Hub's official images from the `docker-library/official-images` library files (through jsDelivr), the newest version of other Docker Hub images from the JSON of shields.io's Docker version badge (it sorts the most recent tags loosely and adds a `v`, so only an answer in the format of the tag or a plain release counts), but only when the setting for images that may be private is on (`possiblyPrivateImages`, off by default), as Docker Hub cannot be asked from the browser whether a repository is public, the versions of GitHub projects from jsDelivr, as GitHub's API allows 60 anonymous requests an hour per address, and release lines from endoflife.date. There is no list of known images: the GitHub project of an image is the one its registry implies (ghcr.io, Crossplane packages; `githubProject`) or the one its `org.opencontainers.image.source` label names, read from the image config Kubescape keeps in the report (`imageSource.ts`, `ImageScan.source`), and only followed for public images (a public-only registry, the `xpkg.upbound.io` packages of Upbound and the Crossplane community, `upbound/` and `crossplane-contrib/`, an image without a publisher only when it is on the list of Docker's official images and its tag is one of the official tags, as an image of that name may also be built locally (`officialImageNames`: one jsDelivr file listing of `docker-library/official-images` a day, so the name of another image goes nowhere; the official tags of a listed name are still read for the newest version), or Quay, Artifact Registry or shields.io knowing the image), so private repository names go nowhere. The project a ghcr.io image implies is only sent to jsDelivr with `possiblyPrivateImages` too: GitHub sets the visibility of a package apart from that of its repository, so a public repository of the same name proves nothing, ghcr.io's anonymous token endpoint (200 for a public package, 403 for a private one) does not allow other sites, and GitHub's API for packages needs a login even for public ones. Other Upbound packages may be private and are also only looked up with `possiblyPrivateImages`, whose switch in the settings warns that it sends the names of internal images to shields.io and jsDelivr. Those requests carry a permit (`possiblyPrivatePermit`, an AbortSignal taken when the lookups of a view start) that switching the setting or the newest versions off revokes (`changeImageVersionSetting`), so requests that wait their turn in the queue of four, or that lookups have yet to make, are not sent; a stopped lookup is not kept as a failure. The other requests carry the permit of the newest versions or of the end of life (`imageVersionsPermit`, `endOfLifePermit`), which a lookup takes as it starts and `changeImageVersionSetting` revokes when `imageVersions` or `endOfLife` is switched off, so the lookups that wait send nothing more to Quay, Google, jsDelivr or endoflife.date; `useImageVersions` takes them when the lookups of a view start and starts no lookup once they are revoked. The endoflife.date product is the one whose identifiers name the image (`pkg:docker`, `pkg:oci`) or its project (`pkg:github`; `purlKey`), or else the product or alias with the name of the image, of the image without a trailing number (`tool3`), of its project, or of the start of its name when the publisher carries it (`tracerproject/tracer-collector`); a product found by name only counts when the tag is one of its release lines. Docker Hub's own APIs and its mirrors (mirror.gcr.io, public.ecr.aws) do not allow other sites. version-checker, when it runs in a cluster, is read from its metrics through the service proxy and takes precedence. Images are only asked about at their own registry or at services that know them publicly; answers are kept a day in localStorage, failures an hour in memory, and at most four requests run at a time. Only a version or "invalid response data" from shields.io shows that it knows an image (`shieldsKnowsImage`); "rate limited by upstream service" and "inaccessible" are failures, asked again after an hour (`shieldsFailure`), not answers kept a day. The requests of the view that opened last go first (`preferNewLookups`), so a page is not kept waiting behind the lookups of a hidden tab. Raise `storageVersion` (`versionCache.ts`) when lookups change, or users keep the answers of the old lookups for a day
- Versions of tags (`versions.ts`): a tag is compared with the tags of the same format (prefix, number of components and variant, so `v3.13.2-distroless` with `v3.15.1-distroless`), project releases only count as numbers with an optional `v` (jsDelivr also lists tags such as `chart-3.0.0`), and a tag with fewer numbers (`8`, `3.4-alpine`) follows its release line, so only a newer line is newer; a single number of eight digits or more is the date of a build, which is never the newest of a release line (alpine tags `3` and `20260805`)

#### 3. Network Policies (`src/networkpolicies/`)
- Network policy visualization with flow diagrams
- Uses `@xyflow/react` and `@dagrejs/dagre` for diagram rendering; nodes are laid out after React Flow measured them
- Each peer is shown once per direction with the ports of all its rules (`policyPeers` in `layout.ts`), as generated policies often have a rule per port with the same peers, such as the passive ports of an FTP server; consecutive ports are shown as ranges (`ports.ts`). The Current policies tab compares the same peers. A rule without peers, which the storage generates for a neighbor with ports but no selector or address, allows its ports from or to any peer: the peer `{}` stands for it (`isAllPeers`), shown as All sources or All destinations, and its traffic (endpoint `anyPeer`) is allowed only by a rule without peers, `unknown` when only rules with peers allow its ports, and blocked when no rule does
- Peers that only differ in per-pod labels (Job runs, rollouts, zones, the pods of a StatefulSet: `statefulset.kubernetes.io/pod-name`, `apps.kubernetes.io/pod-index`; `perPodLabels`) are merged into one node; a peer that has only per-pod labels keeps them (`withoutPerPodSelectorLabels`, used by the diagram, the pod queries of the comparison and `apply.ts`), as an empty selector would stand for every pod of the namespace; more than 5 IP ranges, or more than 10 pods that only differ in label values, of one direction with the same ports share one node
- Private ranges (RFC 1918, 100.64.0.0/10 and IPv6 unique local addresses) are shown as the cluster, other ranges as the internet
- IP blocks are compared as IPv4 or IPv6 ranges (`parseCidr`); ranges of the two families never hold each other. Traffic of a peer without endpoints is `unknown`, not blocked; a peer whose namespace cannot be found is compared by the labels of its selector, and `approximateReason` says why the labels of the generated policy were used. Without permission to list the namespaces, the workload's namespace and those the peers name are read by name (`readNamedNamespaces`); a namespace that cannot be read either is compared by its name only (endpoint `namespaceLabelsUnknown`), which `comparePolicies` says on the flow (`namespace-labels`) only when a namespace selector of the policies of its direction reads other labels than `kubernetes.io/metadata.name`. A pod lookup that failed is `pods-unreadable`, not "No pod has these labels now"
- The list reads the generated policies a namespace at a time, six namespaces at once (`listPerNamespace` in `query.ts`), and shows them as the namespaces arrive: the storage builds the policies of a list from all container profiles it covers within that one request, so one list of the cluster is one long sequential read. Without permission to list namespaces it lists the cluster at once
- The diagram reads the policy once: the storage generates it from runtime profiles that change constantly, so a watch would keep replacing it and restarting the layout
- A generated policy can be downloaded or created in the cluster (`apply.ts`, `NetworkPolicyActions.tsx`), without the labels that differ per run or rollout (`job-name`, `pod-template-hash`), unless a selector would then select every pod. The Create button also checks `get`, as the dialog reads the policy of that name first, and creating or replacing it reads the comparison again (`onApplied` bumps the `reload` of `usePolicyComparison`, which keeps the comparison shown until the new one is read)
- The Current policies tab and the outlines of the diagram compare the observed traffic with the NetworkPolicies of the workload's namespace that select its pod template labels or the labels of one of its pods that run now (`compare.ts`, `policyComparison.ts`, `ExistingPolicies.tsx`): controllers and admission webhooks add labels the template lacks, such as the pod name of a StatefulSet or the labels of a service mesh, so the pods are read with the workload's selector (`readLivePods`; ended pods do not count), their named ports are added to those of the template (an injected sidecar names ports the template lacks), and a policy that leaves out some of the running pods is named in a warning (`selectingSomePods`). A pod is its own template; when the pods of a workload are not read, as a CronJob has no selector, or cannot be read, the tab says that only the pod template was compared (`podsNotRead`). Kubescape names only some labels of a peer, so the peer's live pods are read with a label selector (without per-pod labels, at most 50 queries) and their own labels are compared; peers without pods fall back to the generated labels. Replicas with the same labels apart from per-pod labels count once, with the named ports of all of them: every number per protocol and name (`NamedPorts`, `namedPortKey`), as a rule names a port on its protocol (CoreDNS names 53 `dns` for UDP and `dns-tcp` for TCP). IP blocks are only matched against IP ranges, as whether they apply to pod addresses depends on the network plugin
- Peers with a pod selector but no namespace selector are in the workload's namespace, and the diagram names that namespace
- Main components: `NetworkPolicies.tsx`, `Diagram.tsx`

#### 4. Validating Admission Policies (`src/validating-admission/`)
- Policy playground for testing admission policies
- Uses WASM module for CEL (Common Expression Language) evaluation
- Main components: `ValidatingAdmissionPolicy.tsx`, `EvaluationResultsTables.tsx`
- The test resource can be a sample or an object of the cluster (`clusterResources.ts`)
- Install in cluster (`install.ts`, `InstallPolicyButton.tsx`) creates a copy of the policy (`installedPolicy`) with `failurePolicy: Ignore` and the `valueExpression` of each audit annotation wrapped in `string(...)`, with a binding whose `validationActions` are only Warn and/or Audit, never Deny, and whose `paramRef` has `parameterNotFoundAction: Allow` (the policy checks nothing until its parameters exist). With failurePolicy Fail the API server rejects requests whatever the validationActions for configuration errors (missing parameters with `parameterNotFoundAction: Deny`, a paramKind whose CRD is gone: `CollectParams`, `addConfigError`) and for an audit annotation that fails, and even with Ignore for an audit annotation whose value is not a string or null; a validation or match condition that fails with Fail is a violation, which the validationActions decide about. A namespace limits the binding with its `namespaceSelector` and a `resourceRules` entry with `scope: Namespaced` and `resources: ['*/*']`, as a namespaceSelector never leaves out cluster-scoped objects other than Namespaces. It installs nothing when a binding with Deny refers to the policy's name, also before the policy exists or when it is the plugin's own binding switched to Deny with kubectl, as that binding would enforce the policy of the editor, when another binding of a policy with paramKind has `parameterNotFoundAction: Deny`, or when a binding with the plugin's binding name was not installed by the plugin for this policy (`installProblem`/`checkInstall`, checked when the dialog opens and again before writing). As that check lists every binding, the button also needs permission to list `validatingadmissionpolicybindings`. The `basic-control-configuration` parameters are shared with the policies of the Kubescape library, so the dialog does not create them when a binding with Deny reads them by name or selector (`paramsCreationProblem`), as that binding would start to enforce with them. Policies with a `ControlConfiguration` paramKind need the `kubescape.io/v1` `controlconfigurations` CRD; the `basic-control-configuration` object can be created from the Params tab
- Installing reads the policy and its binding before it writes anything, so a 403 leaves nothing behind, then sends the policy as a dry run (`?dryRun=All`), so a policy the API server refuses, such as one whose expressions do not compile, which the playground does not check, leaves nothing behind either, and then writes the binding at the resourceVersion of the list its Deny check read (a binding changed since fails with a conflict, and one that changed between the list and the read is not written at all) and the policy, and the shared parameters last. The binding comes first, for a new policy and for a policy that the plugin's binding already binds; only a policy that exists without the plugin's binding, such as one of the Kubescape library with failurePolicy Fail, is first replaced by the copy, so a new binding of the plugin never binds a policy the plugin did not write. Install in cluster is enabled by the content of the policy editor, also for a policy that was typed, and says in its dialog when the editor is empty or holds no YAML. Parameters last means a policy the API server refuses leaves no parameters; a write that fails after the first one is a `PartlyInstalledError`, as what was written only warns or audits, or checks nothing; the Install button also checks `get` on both, and `create` or `update` of the binding by whether the binding exists (`checkInstall`). The samples are read with `fetchPluginFile` (`samples.ts`), which reports a failed answer; the sample parameters (`useSampleParams`) and the cluster resource chosen in `ChooseTestResource` only use the answer for the latest choice

#### 5. Runtime Detection (`src/runtimedetection/`, `src/rule-editor/`)
- Runtime security monitoring: alerts (read from Alertmanager), container profiles, rules and rule bindings
- Uses `ContainerProfile` CRDs, falling back to `ApplicationProfile` and `NetworkNeighborhood` on older Storage releases (`src/softwarecomposition/profileApi.ts`)
- Rules and `RuntimeRuleAlertBinding`s use the `kubescape.io/v1` API group; the rule editor tests rules with the `RuleEval` WASM function, which fires a rule as the node-agent does, when every expression of the event type is true (`fired`) and the prefilter of the rule's `state` does not skip the event (`includePrefixes`, `ignorePrefixes`, `ports`, `direction`, `methods`, `excludeProcesses`; `go/rules/prefilter.go`, from the node-agent's `pkg/rulemanager/prefilter`; the result's `prefiltered` says why, and the expressions are still answered), and only evaluates the message and unique id of a rule that fires. The message and the unique id must be strings; a rule whose unique id fails to evaluate does not fire for the node-agent's event types, which the playground says, while the operator alerts without it. The rule form marks an expression as wrong only when it does not compile; one that fails for the sample event it is tried with, such as `event.args[1]` for an event with one argument, gets a note (`isExpressionError` in `ruleValidation.ts`). New Rules objects go to the namespace of Kubescape (`useRulesNamespace` in `rule-editor/kubescapeNamespace.ts`); the editor locks the chart's `default-rules` when it is in that namespace or carries the chart's Helm labels (`isChartDefaultRules`). Its CEL functions (`go/rules/Libraries.go`) follow the node-agent's (`pkg/rulemanager/cel/libraries`): `net.is_private_ip` counts loopback, link-local unicast, RFC 1918, IPv6 unique local, 100.64.0.0/10 and IPv4 from 224.0.0.0, and an argument that is no string is an error
- Seccomp profiles (`SeccompProfiles.tsx`, `seccomp.ts`) come from the `kubescape.io/v1` SeccompProfile CRD or the storage, depending on the operator's `seccompProfileBackend`; with either, the list shows the profiles that were read next to the namespaces that could not be
- Main components: `RuntimeDetection.tsx`, `ApplicationProfileDetail.tsx`, `RuleBindingEditor.tsx`, `rule-editor/RuleEditor.tsx` (the pages; the form is `RuleForm.tsx`, the CEL reference `LibraryReference.tsx`, the test dialog `PlaygroundDialog.tsx` with `ClusterMockLoader.tsx`, the defaults `ruleDefaults.ts` and the syntax check `ruleValidation.ts`)
- The profile page (`ContainerProfileDetail.tsx`) shows the behaviour, the network peers and the full profile as YAML, and the network graph of the workload: the diagram of the network policy the storage generates from the traffic of all its pods (`WorkloadNetworkGraph` in `networkpolicies/Diagram.tsx`, policy name `<kind>-<workload>`). Headlamp's tabs mount every tab hidden, so the graph is only rendered while its tab is open; React Flow would measure hidden nodes as empty. There is no separate network neighborhood page: it showed the same traffic as the Network Policies page, per profile version
- Alert labels of the node-agent (`alertFields.ts`): `severity` is the priority of the rule (1–4 Low, 5–7 Medium, 8–9 High, 10 Critical, 1000 a problem of the node-agent), the workload is only named by `workload_uid` so its name is read from the pod name, and `uid`/`gid` hold memory addresses, which are left out. The table shows the finding (`description`) rather than the summary, and a click on a row opens the details dialog (`AlertDetails.tsx`), which groups the labels by place, process and detection. What a rule detects, its MITRE ATT&CK ids and whether it needs a learned profile come from the `Rules` objects of the alert's cluster (`indexRules`, `alertRule`); the Rule column carries the description in its value, as Headlamp only redraws a cell when its value changes. The dialog links to the profile the container was checked against (`alertProfile.ts`): a profile's `kubescape.io/instance-id` names the version of the pod template (the ReplicaSet, the StatefulSet's `controller-revision-hash`, `<daemonset>-<hash>`, or the Job or CloudNativePG Cluster), which is matched against the pod's owner and labels, or the ReplicaSet in the pod's name when the pod is gone. Otherwise it falls back to the newest profile of the workload's container and says so; Jobs of a CronJob always do, as Kubescape keeps a profile per version of the CronJob. For a DNS alert the dialog shows the domain, which is only in the message (`alertDomain`), and compares it with the domains in the profile's egress (`fetchLearnedDomains`, `compareDomain`): the rule matches names exactly or label by label by a wildcard, as `matchDNSPattern` in `go/rules/match.go` does (a leading `*` and `⋯` are one label, a last `*` one label or more), so `golang.org` alerts when only `proxy.golang.org` was learned, and `a.cdn.example.com` when only `*.example.com` was
- Profiles are kept per version of the pod template (ReplicaSet, controller revision, Job), and the node-agent learns each container for the learning period (24 hours by default, the pod label `kubescape.io/max-sniffing-time` per workload) from its start; `kubescape.io/completion: partial` means it began watching after the container started. Relearn (`relearn.ts`, `RelearnDialog.tsx`, on the profile list and the profile page) restarts a Deployment, StatefulSet or DaemonSet like `kubectl rollout restart`, so its new pods get a new profile learned from their start, and deletes the profiles the workload recorded before. Before restarting, the dialog reads the workload and warns how the restart replaces its pods and when the workload is down (`restartImpact`: replicas, Recreate, OnDelete, a paused Deployment, a StatefulSet partition). When the restart leaves pods running (`leavesPodsRunning`: OnDelete, paused, a partition), deleting the profiles is no longer proposed, as those pods would lose the profile they are checked against; the button waits until the workload and the profiles to delete are read. Trying again after deleting the profiles failed only deletes them (`restarted`), so the workload is not rolled out twice
- Alerts are silenced from a dialog like the exception forms (`Silences.tsx`, `alertmanager.ts`): the rule in one pod, the workload, the namespace or the cluster, for 1 hour to 30 days, with a required reason as the comment and the Kubernetes username as `createdBy`. A silence of a workload matches the names of its pods with a regular expression of the parts Kubernetes generates (`podsOfWorkloadPattern`), so it also covers later rollouts; active silences are listed below the alerts and can be ended. The Silence button of the alerts table opens a dialog kept in `AlertsTab` (`silencing`), as a dialog inside a row goes with the row when a refresh moves it off the page. A silence of a workload whose pod name can be read as a Job of a CronJob or as a pod of a ReplicaSet (a pod template hash of digits only) matches both forms (`podsOfWorkloadPattern`)

#### 6. Exceptions (`src/exceptions/`) & Frameworks (`src/framework/`)
- Security exceptions are `SecurityException`/`ClusterSecurityException` CRDs. The scanners only apply them when the operator's `riskAcceptance` capability is enabled; the plugin then reads the `w/exceptions` control sub-status. Otherwise `apply-security-exceptions.ts` applies them to compliance results client-side, and the Exceptions page warns that scans ignore them
- Exceptions created in the plugin get the Kubernetes username (SelfSubjectReview, `src/common/currentUser.ts`, asked when a form opens and again when it is sent, not kept, as another user may have logged in meanwhile) as `spec.author`; every create and change is appended to the `headlamp.kubescape.io/history` annotation (`history.ts`). The detail page shows that history and the events the scanners record when they apply the exception (`ExceptionMatched` of Kubescape for a control, `VulnerabilitySuppressed` of kubevuln for a CVE; a field selector takes one reason, so `fetchExceptionEvents` picks them from the events of the exception), and says why an exception could not be read
- Risk acceptance: kubevuln hides a finding for `not_affected` and `fixed`, and for `affected` only with an `actionStatement` and responses that are all `can_not_fix`/`will_not_fix`; hidden findings move to `payload.ignoredMatches` with `appliedIgnoreRules` (status in `fix-state`, responses in `justification`, the action in `impactStatement`). The Resources tab and the findings page show which CVEs exceptions cover (`vulnerabilityExceptions.ts`, `exceptionChips.tsx`), and Accept risk creates one exception for the open CVEs of a workload (`GuidedVulnerabilityExceptionForm` with `acceptRisk`), from the Resources tab or the workload page. The image page accepts the risk of the image in the whole cluster: the form without a workload offers only the image scopes, and the page counts only cluster-wide exceptions without namespace, label or resource limits as covering the image (`imageCveExceptions`). Workloads that share an image share its report, into which kubevuln writes the exceptions of the workload it scanned, so ignored matches count as accepted only for a workload whose own exceptions cover them
- The exception edit form keeps the fields of an entry that it does not show (aliases, per-entry `expiresAt`, `subcomponents`), and of the match (`objectSelector`, `matchExpressions` of the namespace selector, `apiGroup` of a resource), which it names as kept, like the expiry of an entry. What the form does not show of an entry or a resource is only kept while the row stands for the same CVE or kind (the aliases, packages and expiry of another CVE, or the `apiGroup` of another kind, would not fit), and a row that is half filled (a resource name without a kind, a label value without a key) is refused instead of left out, which would widen the exception
- Every form that creates or changes an exception has Download YAML next to Create/Save (`ExceptionDialogActions.tsx`), which saves the object Create/Save would send as `<name>.yaml` for a GitOps repository. It needs no permission, so the buttons that open the forms are not limited by permission either; Create/Save are disabled with an explanation where they are denied (`PermittedInClusters`, which checks each cluster of a cluster-wide create). `exportableException` (`exceptionYaml.ts`) leaves out the status, the metadata the API server sets, `ownerReferences`, and the annotations of the plugin's history, `kubectl.kubernetes.io/last-applied-configuration` and `argocd.argoproj.io/tracking-id`; it keeps `spec.author`, as the history records changes in the cluster, which Git's log replaces. The detail page and the list offer the same download for existing exceptions, and the list Download all as YAML: one multi-document file of the selected clusters, in which an exception that is identical in several clusters is written once under a `# Clusters:` comment
- The Exceptions list shows the exceptions of all selected clusters (`useList({ clusters })`); Edit and Delete act in the row's cluster (`SecurityExceptionForm` takes `cluster`)
- Check coverage (`coverageCheck.ts`, `coverage.ts`) reads the scans through `readConfigurationScans` (with `keepOtherClusters`) and `readVulnerabilityScans` (also asking for the selected clusters the cache holds, which it would otherwise drop) and shows per exception what it covers: for posture entries, controls that fail or passed by an exception in the workloads it matches (a control that passes on its own needs no exception); for CVE entries, CVEs in the reports of matched workloads, open or in `ignoredMatches` (an `expiredOnFix` entry whose CVE has a fix has ended; `hasKnownFix` counts listed fixed versions and the fix state `fixed`, and, as kubevuln, a CPE match that bounds the versions from above, which only the full reports of the workload and image pages keep, so the coverage check, which reads the cached reports, misses that one). Exceptions that cover nothing or expired are stale and can be filtered; an exception that exists in several clusters and covers findings in only some names them; clusters whose scans or exceptions were not read completely give Unknown, never stale, and so does an exception that covers nothing while workloads it matches have no vulnerability report, such as one that is missing (`ExceptionCoverage.unscanned`). Scans are indexed once per check by namespace and kind/name, reports once per check by CVE id
- An expiry date ends at the end of that day where the user is (`expiryTimestamp`); an expiry whose date was not changed is kept to the second (`expiresAtFor`)
- Matching follows the scanners and never hides more than they do (`matchesWorkload`): a namespace whose labels are not known matches no `namespaceSelector` (a selector with `NotIn` or `DoesNotExist` would match its empty labels), a selector Kubernetes does not accept (an operator in another case, `In` without values) matches nothing (`selectorIsValid`), and a resource that names an `apiGroup` only matches a kind of that group. Posture entries are matched by Kubescape's rules, vulnerability entries by kubevuln's (`MatchRules`): Kubescape compares the kind, the name and an API group that is given (also an empty one, the core group; the scan names the group in the label `kubescape.io/workload-api-group`) as regular expressions of the whole value, with case, so `kind: deployment` matches nothing and `name: web-.*` matches `web-1` (`patternMatches`: a pattern that does not compile matches nothing, and a leading `*` anything before the rest), takes a Namespace to be in the namespace of its name, and compares control ids without case and as regular expressions (`controlIdMatches`; `WorkloadExceptionMarks` holds them as `ControlIds` and `FrameworksByControl`); kubevuln compares the kind and the API group without case and the name exactly. A vulnerability entry ends at its own `expiresAt`, which overrides that of the exception as in kubevuln (`entryExpiresAt`), so an entry can outlast its exception; `isExceptionExpired` says whether nothing of an exception applies any more, which the list and the coverage check use. Image patterns are tried as kubevuln tries them (`imageMatches`, `patternForms`): also with the registry and the library of Docker Hub that `nginx` or `bitnami/redis:*` leave out, comparing the repository of the reference without case and the tag and digest with case, with `\` escaping the next character (a port of `matchImagePattern`), and a pattern that is not valid matches nothing. The pattern for all tags of an image that is deployed by its digest alone is its bare repository (`toImageGlob`), as `:*` matches no form of such a reference. A resource without a namespace, such as a ClusterRole, gets a cluster-wide exception that names it (`GuidedComplianceExceptionForm`)
- Where the plugin applies exceptions itself, an `alert_only` posture entry leaves the control failed, and an entry limited to a framework (`frameworkName`, compared without case, or as a pattern of the whole name without case, like opa-utils' `regexCompareI`; `patternMatches` in `src/exceptions/patterns.ts`) only applies in that framework, as in Kubescape: the control result keeps those frameworks as the entries write them in `exceptedInFrameworks`, and `isControlExcepted(control, frameworkName)` says whether it is excepted in the framework shown. The scores and counts of `workload-scanning.ts` take the framework (`frameworkComplianceScore` passes its own); the other compliance pages use the framework chosen on the Compliance page (`selectedFrameworkName`). The combined view of all controls (Full Regolibrary) is no framework. Where the scanner applies them, a control that fails with the sub-status `w/exceptions` is not excluded (`markScannerExceptions`): an `alert_only` entry acknowledged it, or another rule of the control still fails
- `fetchSecurityExceptions` reports what it could not read in `errors` (a 404 means the CRDs are not installed, so no exceptions); `useSecurityExceptions` returns them per cluster and the pages show them (`ExceptionReadErrors`), as findings may otherwise be shown as open although an exception covers them. That includes the workloads an `objectSelector` selects, which are listed per allowed namespace for a restricted user, and the labels of the namespaces, which are read per allowed namespace when the namespaces cannot be listed
- The overview and notifications also report the entries of an exception that expire on their own (`ExceptionExpiry.entries`): an entry that outlasts the exception at its own expiry, and the exception's expiry then by the entries that end with it (its posture controls and the CVEs without an expiry of their own) instead of as the whole exception (`expiringExceptions`). The detail page says when entries outlast an expired exception and shows the expiry of each vulnerability entry
- Custom frameworks are listed in the Kubescape namespace (`listCustomObjectConfigMaps`, also on the Frameworks page), where a user who may change them can list them; a ConfigMap is deleted and edited in its own namespace (`configmapNamespace`, passed to the editor as `?namespace=`), and a hand-edited `controlsIDs` gives a framework without controls (`parseControlIDs` in `src/framework/customFrameworks.ts`); `getKubescapeNamespace` looks in the allowed namespaces, or `kubescape`, when pods cannot be listed in all namespaces. It finds the namespace by the operator pod (`app.kubernetes.io/name=kubescape-operator,app.kubernetes.io/component=operator`), then any pod of the chart (`kubescapePodSelectors`), one lookup per cluster at a time; `useKubescapeNamespace(cluster?)` follows the current cluster. With allowed namespaces, the SecurityExceptions of each of them are read (`fetchSecurityExceptions`), as such a user may not list them in the whole cluster
- Custom compliance frameworks are stored as ConfigMaps in the Kubescape operator namespace
- The frameworks whose scores the Compliance page and the Overview show (`activeFrameworks`, and `framework`, the one the Compliance page opens with) are chosen on the settings page (`FrameworkSettings.tsx`, inside a `RegoDataProvider`, as the settings page is no route of the plugin) or with the Frameworks menu of the Compliance page. The settings page offers Kubescape's frameworks and the custom frameworks found in the Kubescape namespace of every configured cluster (`customFrameworkNames`; a cluster that cannot be read adds none), and keeps the page's framework while it is chosen, else the first one chosen (`chooseFrameworks`). Headlamp saves these settings with the Save button of the settings page. The Overview scores custom frameworks too (`useCustomFrameworks`, `fetchCustomFrameworks`, which the Compliance page shares), and the Compliance page names chosen frameworks that its cluster does not have once its custom frameworks are read (`customFrameworksRead`). Frameworks a GitOps repository provides as such ConfigMaps (label `kubescape.io/custom-object: framework`) show up like those of the editor; an edit in the plugin is undone by the repository. A framework ConfigMap labelled `kubescape.io/default-framework: "true"` is one of its cluster's defaults (`isDefaultFramework`, `FrameWork.isDefault`): while the user chose no frameworks, the Compliance page, the Overview and the settings page show the cluster's default frameworks instead of Kubescape's (`activeFrameworkNames(activeFrameworks, customFrameworks)`, `shownByDefault`); a choice of one's own wins. The page still opens with all controls by default, as `framework: ''` cannot tell a choice of Show all from no choice

### Data Flow Patterns

#### API Integration
- **Custom Resources**: All data comes from Kubescape CRDs in `spdx.softwarecomposition.kubescape.io/v1beta1` API group
- **Pagination**: Large datasets handled with continuation tokens (`src/query.ts`). The Cancel button of the progress takes `useCurrentReadFlag`, which always stops the page's current read, also after the page started a new one without drawing again. With allowed namespaces, each namespace is read to its last page; a namespace that cannot be read leaves the others and stays on the task (`failedNamespaces`, continuation `''`), so the next read reads only those namespaces again; it does not stop the tasks after it. Pages share their tasks between pages, so each page is read once (`task.reading`), and a page that failed keeps its continuation for the next read and leaves `task.error`, which pages show with `queryTaskErrors`. The progress goes to the page that asked to read last and still reads: the vulnerability reads keep a reporter per read (`progressReporters`), so a search that is closed gives the progress back to the page that waits for the same reports; the compliance reads have one `reportProgress`, as only route pages read the configuration scans and Headlamp shows one route at a time. Each read gets its own `continueReading` flag, so a read for clusters selected before stops
- **Per namespace**: the Compliance task and the vulnerability summaries task read with `readPerNamespace` (`src/query.ts`) as their `read`: a namespace at a time, six at once, each to its last page and handed to the task at once, as the storage decodes the objects of one list one after the other. It reads the allowed namespaces, or else only the namespaces that have objects, found once (`pendingNamespaces`) by a list of the task's class without `fullSpec` (metadata only, which the storage answers from its index; pages of 1000, listed again when a read stops between them); when that list fails, it lists the namespaces of the cluster, and without permission to list them, or with none, it pages the whole cluster (`clusterWide`). A stopped read leaves the unread namespaces for More scans; namespaces that failed set `failedNamespaces` and the error (three named), so the tasks after it still read, and are read again next time
- **fullSpecListQuery** reads all pages of a class with their spec; the seccomp profiles of the storage need it. It returns `{ items, errors }` like `listQueryWithErrors`: allowed namespaces that cannot be read, or a page after the first, are named in the errors, and it rejects when nothing could be read
- **No watches on storage objects**: do not read Kubescape storage objects with `useApiGet`/`useGet`: they watch the object after reading it, and the storage sends watch events without the data of the spec (a WorkloadConfigurationScanSummary with `controls: null` and zero severities, a report without its matches), or refuses to watch the summaries of a namespace (`configurationscansummaries`, `vulnerabilitysummaries`) with 405, after which Headlamp reconnects endlessly. Read them once with request: `useStorageObject` (`src/common/readOnce.ts`) reads an object once per class, name, namespace and cluster (the cluster of the URL when none is given, as `request` with an empty cluster goes to no cluster), with `loading`, `error` and `reload`
- **fullSpec**: the Kubescape storage returns only the metadata of listed objects, unless the list asks for `resourceVersion=fullSpec` (`paginatedListQuery` does, `listQuery` does not). Use `listQuery` for lists that only need names, labels and annotations; anything that reads `spec` needs `paginatedListQuery`. Generated network policies are the exception: the storage generates them from the container profiles it reads with their spec, whatever the list asks. `listQueryWithErrors` returns `{ items, errors }` naming the namespaces that could not be read, which `useItemsInClusters` shows; `listQuery` only logs them
- **Multi-cluster**: list pages query all selected clusters (`useItemsInClusters` in `src/common/clusters.ts`; the Exceptions list with `useList({ clusters })`) and link to details with `activeCluster`, except to the configuration scan of a workload and its fixes: those routes name the cluster of the scan in their path too (`/kubescape/compliance/:cluster/...`), and Headlamp's `Link` puts all selected clusters (`b+a`) in every `:cluster` for an `activeCluster`, so links to them pass `params.cluster` only; detail and editor pages use the cluster in the URL
- **Namespace filtering**: Respects Headlamp's namespace access controls

#### Data Relationships
```
Vulnerability Flow: Namespace → VulnerabilitySummary → VulnerabilityManifestSummary → VulnerabilityManifest → SBOMSyft
Configuration Flow: Namespace → ConfigurationScanSummary → WorkloadConfigurationScanSummary → WorkloadConfigurationScan
```

### WASM Integration

#### Purpose
Provides CEL evaluation for Kubernetes ValidatingAdmissionPolicies without requiring cluster deployment.

#### Architecture
- **Go Backend** (`go/cmd/main.go`): Compiled to WASM, implements CEL evaluation engine
- **JavaScript Bridge** (`src/wasm/initWasmModule.ts`): Initializes WASM module and exposes functions
- **Build Process**: `GOOS=js GOARCH=wasm go build -o dist/main.wasm cmd/main.go`

#### Key Functions
- `AdmissionEval`: Evaluates admission policies against test resources
- Matches like the API server: resource rules with `resourceNames` and `scope`, `excludeResourceRules`, `namespaceSelector` (on the namespace object, on a Namespace itself, not on other cluster-scoped objects) and `objectSelector` (object or old object); `matchReason` says why a request does not match. A match condition that fails, while none is false, is `matchConditionError` and applies the `failurePolicy`: Ignore admits the request, Fail makes it a violation that the validationActions of the binding deny, warn about or audit. `matchConditionsMatched` is false when a match condition is false. Match conditions cannot use `variables` (the API server refuses such a policy; reported as `error`). `params` and `namespaceObject` are null when their editors are empty, and `namespaceObject` is always null in a match condition, as the API server gives match conditions no namespace. Whole numbers of the object, the parameters and the namespace are integers, as the API server reads them (`unmarshalObject`). The request of a Namespace names it as its namespace. Resource patterns are compared as they are written, with their case. An object without a namespace is cluster-scoped when its kind is a known cluster-scoped one; otherwise its scope is guessed (cluster-scoped for a kind that starts with Cluster, else namespaced; `resourceScope`), and `matchReason` says so when the guess decided. The message of a violation is made like the API server's (`failureMessage`): the trimmed messageExpression unless it fails, is not a string, is empty, is longer than 5 KiB or contains a line break, else the trimmed message, else `failed expression: <expression>`. `auditAnnotationError` names an audit annotation for which the API server rejects the request whatever the validationActions: a value that is not a string or null (also with Ignore), or a failure with Fail. `messageExpression` comes before `message`. Resources are guessed from the kind (`makePlural`: ingresses, networkpolicies, gateways, endpoints)
- The module is loaded once (`loadWasm`, `useWasm`), and a panic in Go becomes an error result instead of stopping the program
- In `AdmissionEval`, expressions are parsed but not type-checked, and the Kubernetes CEL libraries (quantity, regex, ...) are not included
- `RuleEval`: Evaluates runtime detection rules against a mock event, profile, network and Kubernetes mock (`apiServerAddress`, `pods` with the fields of Pod objects). Expressions are compiled with the checker, as the node-agent compiles them, so unknown functions, overloads and fields of the event are errors also where they are not reached (`compileError` on the result tells them from an error of evaluating against the event). The event is an object with the fields and types the node-agent declares (`go/rules/event.go`, from `pkg/utils/cel.go`): `pid`, `ppid`, `uid`, `cmd`, `attrSize`, `ttyMajor` and `ttyMinor` are unsigned, so `event.pid == 1` does not compile and `event.pid == 1u` does; a field the mock leaves out has its zero value; the library functions take the argument types the node-agent declares (`process.get_process_env(int(event.pid))`). Whole numbers of an admission request are integers. `go/rules/Libraries.go` declares the node-agent's functions from one table as `cp.*` and the deprecated aliases `ap.*` and `nn.*`, with `k8s.*`, `parse.*` (also `get_exec_path(args, comm, exepath)`), `net.*` and `process.*`. Like the node-agent's `isExecInPodSpec`, `cp.was_executed` and `cp.was_executed_with_args` also count, for a container with a profile, an element of the `command` or of a `preStop`/`postStart` exec hook of its container in the Kubernetes mock, whose pod and container are known only for the event's `containerId` (by its `namespace`, `podName` and `containerName`). `go/rules/match.go` ports the node-agent's matching: paths with `⋯` and `*` and one trailing slash, exec arguments with `⋯`/`⋯⋯`, canonical IPs, CIDRs and `*`, and domains with or without the trailing dot and with wildcards. `k8s-admission` rules are evaluated in the operator's environment (variables `object`, `oldObject`, `options`, `params`, its CEL extensions, none of the node-agent's functions), and `dnsQuery` expressions with `eventType` `dns`. `go/rules/testdata/default-rules.yaml` is the chart's default rules, which `TestEvaluatesTheDefaultRulesOfTheChart` evaluates

## Important Development Notes

- **Permissions**: actions that change the cluster are wrapped in `Permitted` / `PermittedIconButton` (`src/common/permissions.tsx`), which ask a SelfSubjectAccessReview and disable the action with an explanation when it is denied; `Permitted` also takes several checks and names the first one denied. That includes the save buttons of the editors (custom frameworks with `frameworkCheck`, as their ConfigMaps live in the Kubescape namespace; Rules objects in the namespace of the form, or of the object an edit replaces; rule bindings) and the buttons that open them for a new object; `PermittedIconButton` takes `size="medium"` next to a page title. An unanswered check leaves the action enabled. `useCanI`, `useDeniedCheck` and `useCurrentUser` follow the cluster of the address when none is given. The buttons that open the exception forms (Exclude CVE, Create exception, Accept risk) are not wrapped in `Permitted`: the forms also offer Download YAML, which needs no permission (read-only users, GitOps), and check the permission to create the exception themselves. `useCanI` and `useDeniedCheck` return nothing (unknown, so the action stays enabled) for a new check or cluster until it is answered. Answers are kept for ten seconds per cluster and check (`answerLifetime`), as logging out and in as another user does not reload the plugin (Headlamp's `logout` only clears the token and its query cache), so tests that need another answer use another cluster name (`RuntimeDetection.test.tsx` overrides `getCluster` with `mocks.currentCluster` for that). A function returned from `beforeEach` is called as a cleanup after each test, so a hook like `beforeEach(() => post.mockReset())` calls the mock once more without arguments; give it a block body. The delete buttons of the Rules and Rule Bindings tabs and of custom frameworks open `ConfirmDeleteDialog` (`src/common/ConfirmDeleteDialog.tsx`), which names the object, its namespace and cluster and what deleting it changes, before anything is deleted

- **Big clusters**: per-control results (`countScans`, `controlComplianceScore`, ...) come from an index built once per array of scans (`workload-scanning.ts`); call `invalidateControlStats()` after changing `exceptedByPolicy` marks in place. Aggregate with maps keyed by id, not `find`/`some` inside loops, memoise derived table data, and give table columns plain values (`accessorFn`) with JSX in `Cell`, which only renders for the rows on the page. The vulnerability cache keeps only the declared fields of each match (`toImageScan`)

- **Tables**: use `src/common/Table.tsx` instead of Headlamp's `Table`; it keeps the sorting of each table for the session. It offers the rows per page of Headlamp's settings (`tableRowsPerPageOptions`, 15, 25 and 50 unless the user adds a size): Headlamp keeps the size chosen in any table as that of all its tables (localStorage `tables_rows_per_page`), so a size of the plugin's own turned up in Headlamp's lists, whose choices lacked it. Headlamp names a column without an `id` by its index; the plugin's table gives such a column its header as id (`withColumnIds`; not a header that is empty, a number or already taken), so a saved sorting stays on its column when a column appears before it. Give the columns used in `initialState.sorting` an explicit `id` all the same, as a header can change. The table switches off the ranking of search results (`enableGlobalFilterRankedResults`): to rank them, the table clears the sorting while the search box has text, which would be saved as the user's choice. `onRowClick` makes the rows clickable: Headlamp's table replaces the table-wide `muiTableBodyCellProps` with its own and renders rows with `display: contents`, so the click is set on the cells of each column (`withRowClick`). Headlamp only redraws a cell when its value changes, so a cell keeps the handlers of the item it first showed: tables with clickable rows or row actions need a `getRowId` per item, and action columns a value per item. The table also keeps the values of a row until `data` changes, so values that arrive later, such as the image versions, must be part of the rows (new row objects) rather than read from state in an `accessorFn`. The Upgrades tab keys rows by image, package and installed version (`upgradeRowId`). Cells with an exception chip take `exceptionChipValue` or `acceptedChipValue` as their value, which carry what the chip and its tooltip show; a text value that sorts by a number takes a `sortingFn`; TanStack picks the automatic sorting function from the rows after the tenth, so columns whose text holds numbers name theirs (`alphanumeric` for the counts and `N of M`, `basic` for the end of life). The search of the table only covers a column whose value in the first row is text or a number, so accessors return `''` instead of undefined. A column that is left out is spread conditionally (`...(condition ? [column] : [])`): an empty `{}` shows as a column without a header. A link to the `dataSource` of a report goes through `DataSourceLink` (`CVESummary.tsx`), which only links `http(s)` addresses

- **Read statistics**: `ReadRecorder` (`src/common/readStatistics.ts`) records per read, cluster and phase (`summaries`, `report versions`, `cached reports`, `reports`, `configuration scans`, `security exceptions`) the objects, those from the cache, requests, failures and duration, into every read in progress, as reads share their tasks. The Vulnerabilities and Compliance pages show one line after a read (`vulnerabilityReadSummary`, `configurationReadSummary`), and `console.info` logs each phase; `readVulnerabilityScans` and `readConfigurationScans` take `onStatistics`

- **Links**: Headlamp's `Link` takes no ref and replaces the `onClick` of its caller with its own, so neither works on it: navigate with `useHistory` and `Router.createRouteURL`, or put the state in the address (`search`). The search's results are react-router `Link`s, and Enter opens the first result, computed from the results; outside of a cluster, where `createRouteURL` gives Headlamp's home page for a page of the plugin, the results (controls) are no links and Enter opens nothing; the Overview's All upgrades link opens `?tab=upgrades` (`vulnerabilityTabSearch`)

- **Service proxy**: requests through the service proxy (Prometheus, Alertmanager, version-checker, profiles) pass `autoLogoutOnAuthError: false`, and `isJSON: false` where the service answers without a body, as Alertmanager does when a silence is ended (`expireSilence`); the permission check of the Alertmanager proxy names the service with its port (`alertmanagerProxyCheck`), as a role may allow that service only: Headlamp logs the user out on a 401 by default, and a 401 from a proxy in front of the service, such as kube-rbac-proxy, does not mean the session ended

- **Settings**: the settings page merges every change into the latest settings (`changeData`), as Headlamp replaces the whole settings object, so an auto-detection that finishes late keeps what the user changed meanwhile

- **Tests**: Headlamp's `lib/k8s` modules do not resolve in tests; `src/common/clusterContext.ts` re-exports `getAllowedNamespaces` and `src/common/clustersConf.ts` `useClustersConf`, so tests can mock them. Caught errors are `unknown`: read them with `errorMessage`, `errorStatus` and `errorName` (`src/common/errors.ts`) `src/common/fakeIndexedDB.ts` is an in-memory IndexedDB for tests (`installFakeIndexedDB`, with `failOpen`, `blockOpen` and `failWrites`); call `resetPluginDatabase()` and `resetReportCacheState()` between tests, as the database and cluster identities are kept per session.

- **Prerequisites**: Requires Kubescape operator installed in target cluster with `continuousScan: enable`
- **Testing**: Plugin requires live Kubernetes cluster with Kubescape CRDs for full functionality
- **Multi-cluster**: Plugin supports Headlamp's multi-cluster features with backward compatibility
- **Security**: All Kubernetes API access goes through Headlamp's secure proxy, no direct cluster access
- **Build Dependencies**: WASM build requires Go installation; frontend build only requires npm
- **File names**: no two modules in a folder may differ only in case (`relearn.ts` next to `Relearn.tsx`): on Windows `./Relearn` then resolves to `relearn.ts`, and the import is undefined
- **API Groups**: Most CRDs use `spdx.softwarecomposition.kubescape.io/v1beta1`. The `SecurityException` and `ClusterSecurityException` CRDs use `kubescape.io/v1beta1` (operator-owned, defined in `src/softwarecomposition/SecurityException.ts`).

## Release Process

Use GitHub workflow `pre-release`:
1. Specify version (e.g., v1.0.0)
2. Workflow builds tar and container image
3. Updates `artifacthub-pkg.yml` and `package.json`
4. Generates tag and release
5. Manually update release notes and unflag pre-release

The workflow checks the release name, runs the CI checks before building, and tags the release commit it pushes. Renovate only raises `scripts/data-sources.json` (`enabledManagers: custom.regex`); Dependabot updates npm, Go modules and actions. The CI publish job only runs in the kubescape organisation. CodeQL builds the Go code natively and with `GOOS=js GOARCH=wasm`.
